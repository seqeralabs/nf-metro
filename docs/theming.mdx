A theme decides how a map looks: colors, fonts, station glyphs, section boxes, the legend frame, and optionally layout spacing.
It never changes what the map says.

## Concepts

**Theme.** A named set of [fields](#field-reference), written as a YAML file.
Every built-in theme is such a file in `src/nf_metro/themes/`, loaded and checked exactly like one you write yourself.

**Mode.** Most themes have a light and a dark palette.
An SVG carries both and follows the viewer's `color-scheme` (see [Light and dark in one SVG](#light-and-dark-in-one-svg)).
`%%metro mode:` or `--mode` picks the palette baked into a PNG or a single-palette export.

**Stack.** A theme value is a comma-separated list of themes, applied left to right.
A later theme wins for every field it sets, and the light and dark palettes merge separately.
A single name is a stack of one.

**Base.** Every stack starts from the `nfcore` theme, so a theme only needs to set the fields it changes.
A map with no `%%metro style:` renders with `nfcore` alone.

**Layout block.** A theme can also set some layout options, such as spacing.
The order of precedence is: a command-line flag, then a `%%metro` directive in the map, then the theme, then the built-in default.

## Using a theme

Set the theme in the map, or on the command line:

```text
%%metro style: london-tube
```

```bash
nf-metro render pipeline.mmd -o pipeline.svg --theme london-tube
```

`--theme` replaces the map's `%%metro style:` entirely.

| Theme         | Look                                                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `nfcore`      | The default and the base: bold labels, filled section boxes with number badges, white station pills.                              |
| `seqera`      | Seqera brand colors and Inter type.                                                                                               |
| `london-tube` | A schematic transit look: square tabs for one-line stations, rings at interchanges, bundled lines edge to edge, unboxed sections. |
| `transparent` | One palette on a transparent canvas, for embedding. Ignores the mode.                                                             |

Add `-light` or `-dark` to `nfcore`, `seqera` or `london-tube` to pin the baked palette, for example `nfcore-light`.
`dark` is also accepted for `nfcore`, and `light` for `transparent`.

## Stacking themes

```text
%%metro style: seqera, london-tube
```

This map takes the station glyphs, section style and fonts from `london-tube`, and every field `london-tube` leaves unset from `seqera`.
Under both lies the `nfcore` base, which supplies anything neither sets.

A built-in theme sets only the fields its file lists.
`london-tube, nfcore` therefore keeps the `london-tube` station tabs and rings, because `nfcore` does not set `station_glyph` or `interchange_glyph`, but takes the `nfcore` colors.

## Writing your own theme

1. Create a YAML file whose name ends in `.yaml` or `.yml`.
2. Give it a `name`, then set the fields you want to change.
   Top-level fields apply to both palettes, and `light:` and `dark:` blocks override them for one palette.
3. Optionally, start from another theme with `extends:`, and set layout options in a `layout:` block.
4. Add the file to a stack.
   In `%%metro style:` the path is relative to the `.mmd` file; on the command line it is relative to the working directory.

```yaml title="house_style.yaml"
name: house-style
extends: london-tube # optional: a name, a file, or a list

label_font_size: 13
station_glyph: tick

light:
  label_color: "#5a2d82"
  legend_stroke: "#5a2d82"
dark:
  label_color: "#e5d4f5"
  legend_stroke: "#e5d4f5"

layout:
  y_spacing: 45
```

```text
%%metro style: house_style.yaml
```

`extends:` is shorthand for listing those themes earlier in the stack, so the line above is the same as `%%metro style: london-tube, house_style.yaml`.

A theme with one palette sets `fixed_mode: light` or `fixed_mode: dark`.
It then renders that palette whatever mode is asked for, and its SVG does not adapt to the viewer.
In a stack, `fixed_mode` behaves like any field: a later theme that sets it, to a mode or to `none`, replaces an earlier one.
The built-in `nfcore`, `seqera` and `london-tube` set `fixed_mode: none`, so `transparent, seqera` adapts to the viewer again.

nf-metro checks the whole file before it renders anything.
An unknown field, a value of the wrong type, a color it cannot read, an unknown `layout:` option, or two files that extend each other stops the render with an error that names the problem.

<Aside type="caution" title="Label size">

Layout reserves room for station labels from the map's own settings, not the theme.
A theme that sets `label_font_size` much above 13 can make labels collide.
Use the layout option `font_scale` instead, which layout does account for.

</Aside>

### Fonts

The SVG names the theme's font and the viewer's browser draws it, so name a font your readers have, followed by fallbacks.
`london-tube` asks for Gill Sans, which macOS and Windows with Office have.
PNG output, `--embed-font` and `--text-to-paths` draw every theme in the bundled Inter face, so the output is the same on any machine.

## The built-in themes

The built-in themes are the best worked examples of the format.
Each is a short file in [`src/nf_metro/themes/`](https://github.com/seqeralabs/nf-metro/tree/main/src/nf_metro/themes).

- `nfcore.yaml` is the base.
  It sets every field the schema leaves without a default, so it is the template for a complete theme.
- `seqera.yaml` replaces the fonts, sizes and both palettes, and leaves the shapes alone.
- `london_tube.yaml` changes shapes as well as colors, and is the example to copy for a different look.
  Its geometry follows the construction rules of TfL's [Line Diagram Standard](https://content.tfl.gov.uk/tfl-line-diagram-standard.pdf), which measures everything in multiples of the line width: an interchange ring has a 2-wide inside and a 0.5-wide outline, a chain of rings is bridged by a 0.5-wide strip, and lines on separate tracks are joined by a dumbbell link.
  Rings also mark cross-track `%%metro interchange:` stations and multi-rail stations in rail mode.
  The theme deliberately uses track-weight tabs rather than the standard's 0.66 square: a tab is 1 line width thick and reaches 1.5 past the line, so it reads as a continuation of the track, and the terminus bar matches it.
  Lines on a shared track are drawn edge to edge, as in the standard, so the theme sets no `track_gap`.
  Inactive lines are 30% grey.
- `transparent.yaml` sets `fixed_mode: dark` and `background_color: none`, for maps embedded on a page that supplies its own background.

```yaml title="london_tube.yaml (abridged)"
name: london-tube

station_glyph: tick
station_tick_width: 1 # track-weight tabs
station_tick_length: 1.5
interchange_glyph: ring
line_width: 4
label_font_weight: normal
section_stroke_dasharray: "6 4"
section_badges: false
section_label_uppercase: true
legend_stroke_width: 1.5

light:
  background_color: "#ffffff"
  label_color: "#1c3f94"
  ring_color: "#000000"
  ring_fill: "#ffffff"
  muted_line_color: "#b3b3b3"
  section_fill: transparent
  legend_stroke: "#000000"
dark:
  background_color: "#10141c"
  label_color: "#dfe6ff"
  ring_color: "#ffffff"
  ring_fill: "#10141c"
  muted_line_color: "#585a60"
  section_fill: transparent
  legend_stroke: "#ffffff"
```

## Light and dark in one SVG

An nf-metro SVG has no separate light and dark version, and nf-metro never re-renders it when the viewer's theme changes.
Every themeable color is baked into the file as a pair, and native CSS picks the right half at display time:

![Diagram: light-dark(#fff, #1a1a1a) resolves to #fff under a light color-scheme and to #1a1a1a under a dark one](assets/theming_resolution.svg)

<Aside type="note" title="The short recipe">

1. Use `light-dark(light, dark)` for every color that should adapt.
2. If the file needs to work standalone, meaning opened directly or dropped into a host with no opinion on theme, declare `color-scheme: light dark` on the root.
3. If you inline it into a page you control instead, leave that declaration off the root.
   The SVG then inherits the page's `color-scheme`.
   Declaring it yourself would override the host's choice rather than follow it.
4. If you reference it with `<img>` instead, the host page can still steer the colors by setting `color-scheme` directly on the `<img>` element.
   This is the safe way to embed content you do not fully trust, because it blocks scripts and external loads.
   Chromium and Firefox honor the setting regardless of what the SVG itself declares.
   Safari does not.
   It always shows the viewer's own OS setting instead of the host's.
   A Safari reader still gets a readable map, and no authoring step closes that gap.

</Aside>

## `light-dark()` and `color-scheme`

`light-dark()` takes two color values and resolves to one of them.
It works on any color property, which lets it drop straight into SVG presentation attributes and `<style>` rules:

```css
fill: light-dark(#ffffff, #1a1a1a);
```

It resolves against the element's used `color-scheme`.
If nothing declares one anywhere, it still resolves, but against the browser's own default, which is generally light rather than the viewer's OS preference.
Declare one to let that preference in:

```css
:root {
  color-scheme: light dark;
}
```

`light dark` means "both are supported here, so pick whichever matches the current preference".
Pinning one side instead (`color-scheme: dark`) forces every `light-dark()` under it to that value regardless of preference.
That is the deterministic escape hatch for a case such as a PNG export.

## `var()` for host overrides (optional)

```css
/* [!callout /--my-bg/] A host page sets this to override the color. */
/* [!callout /light-dark/] Used when the host sets nothing. */
fill: var(--my-bg, light-dark(#ffffff, #1a1a1a));
```

A page embedding the SVG (the **host page**) can set `--my-bg` on a wrapper to override the color outright.
If it doesn't, the light/dark pair still runs.
This layer is optional, because `light-dark()` plus `color-scheme` is the whole mechanism.
nf-metro calls the properties it exposes this way **chrome**: background, title, labels, section boxes, and legend.
[Chrome colors and host overrides](#chrome-colors-and-host-overrides) lists the custom property for each.
Line and route colors carry meaning, and they stay fixed.

## Where `color-scheme` should live

`color-scheme` is **inherited**.
An element with no `color-scheme` of its own takes its ancestor's computed value, the same as `font-family` or `color` normally would.
Redeclaring it resets what "current preference" means for everything below.
An element that sets its own `color-scheme` therefore stops inheriting and starts from scratch.
That matters once the SVG is embedded, because the host page and the SVG can disagree about who owns the decision.
nf-metro has two modes, controlled by `self_color_scheme` on `render_svg` (`--no-self-color-scheme` on the CLI):

**Standalone (the default).** The root `<svg>` declares its own `color-scheme` (`src/nf_metro/render/svg.py:2595-2597`):

```html
<svg style="color-scheme: light dark"></svg>
```

`light-dark()` then resolves against **the viewer's OS or browser preference**.
That is the right behavior for a file opened on its own, or dropped into a page that has no opinion about theme.

**Embedded in a page that already manages theme.** Passing `--no-self-color-scheme` omits that declaration, and the `<svg>` inherits `color-scheme` from its host instead.
Every `<Metro>` embed on this docs site uses it (`website/src/lib/render-metro.mjs:277`).
This site's theme picker sets `color-scheme` on `<html>`:

```css title="reset.css (Starlight)"
html {
  color-scheme: dark;
}
html[data-theme="light"] {
  color-scheme: light;
}
```

This map has no `color-scheme` of its own, and it follows the picker.
Switch the theme in the nav to see it change, independently of your OS setting:

<Metro src="examples/guide/01_minimal.mmd" clean />

The two modes are not interchangeable.
An embedded SVG that declares its own `color-scheme: light dark` ignores a host's forced single value and falls back to the OS preference whatever the host's toggle says.
Redeclaring `light dark` reopens both options, which reverts the "current preference" it resolves against to the browser or OS signal.
`--no-self-color-scheme` exists for that reason.
Leaving the property off the SVG root is what lets a host's manual toggle reach it at all.

The flag only decides _whose_ preference wins.
Something still has to supply a `light-dark()` pair to resolve in the first place.
That is the separate job of the chrome CSS from the `var()` ingredient described earlier.
Both have to be right for an embedded map to stay theme-adaptive.

<Aside type="tip" title="What this docs site itself passes">

From `renderMetroFile` (`website/src/lib/render-metro.mjs:254-296`):

| Flag                     | `<Metro>` embed | OG image export |
| ------------------------ | --------------- | --------------- |
| `--no-self-color-scheme` | always          | always          |
| `--no-chrome-css`        | never           | always          |

`--no-chrome-css` bakes chrome colors to one concrete value.
An inline embed that passed it would leave no `light-dark()` pair for `--no-self-color-scheme` to act on.
It is reserved for the OG-image path, which needs one fixed image rather than a page-following one.
The site also passes `--no-manifest` to every embed here, but that only skips per-node metadata `<Metro>` doesn't use and has no effect on theming.

</Aside>

## The transparent-background fallback

A transparent-background theme has no `--nfm-bg` pair to lean on.
Text drawn straight onto the canvas, such as titles and section labels, can therefore turn illegible against the host page's background.
For that one case nf-metro adds a second, coarser path built on `prefers-color-scheme`.
That media query branches a whole stylesheet rule, rather than a property like `color-scheme` that `light-dark()` resolves per value (`src/nf_metro/render/svg.py`, `_inject_dark_mode_style`):

```css
@media (prefers-color-scheme: dark) {
  .nf-metro-section-label {
    fill: #d0d0d0;
  }
  .nf-metro-title {
    fill: #ffffff;
  }
}
```

`--no-dark-mode-css` turns it off, for a host whose own theming it would otherwise fight.

In `--format html` output the page paints the canvas itself, so these rules use `light-dark()` instead of the media query.
They then follow the page's mode rather than the OS setting.

<Aside type="note" title="One theme opts out of all of this on purpose">

nf-metro ships one theme with no light/dark pair at all: `transparent` (also accepted as `light`), whose file sets `fixed_mode`.
Every `--nfm-*` fallback is a single baked value, no `light-dark()` appears anywhere, and `self_color_scheme` has nothing to do, because no `color-scheme` gets declared either way.
The media query described earlier is the only adaptation such a theme gets.
Choose it deliberately rather than by leaving `--theme` or `%%metro style:` unset.

</Aside>

## Consumers that cannot parse `light-dark()` or `var()`

Some SVG consumers parse a restricted CSS subset and abort outright on `light-dark()` or `var()`.
`--format png` handles this for you; when you hand the SVG to an external tool, the export flags map directly onto the ingredients described earlier:

```bash
# bake one concrete palette; no var()/light-dark() left to choke on
nf-metro render pipeline.mmd -o pipeline.svg --no-chrome-css --mode light

# pin color-scheme for a consumer that DOES understand light-dark(),
# so the result is deterministic rather than following its own environment
nf-metro render pipeline.mmd -o pipeline.svg --mode dark
```

Full flag reference: [Embedding](/nf-metro/embedding/).

## Referenced versus inline SVGs

**Inline** means the host page contains the SVG markup directly, rather than referencing it by URL:

```html
<!-- referenced: a separate document -->
<img src="map.svg" />

<!-- inline: part of this document -->
<svg>
  <rect fill="light-dark(#fff, #1a1a1a)" ... />
</svg>
```

`<img>` loads the SVG into its own document, and ordinary CSS stops at that boundary.
Custom properties, cascade, and inheritance do not cross it, and `var()` overrides never arrive.
`color-scheme` is the one deliberate exception.
Per [Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#prefers-color-scheme), an `<img>`-loaded SVG resolves `prefers-color-scheme` and `light-dark()` against **the used `color-scheme` of the `<img>` element** rather than the OS preference.
That overrides even the SVG's own `color-scheme: light dark`.
Chromium and Firefox honor this deterministically, independently of the OS preference.

Safari does not.
It ignores the declared `color-scheme` on the `<img>` entirely and follows the real system preference instead, as if no override were present.

`<object>` and `<embed>` do not get this either, because they open a full nested browsing context, which the spec excludes.
Do not rely on either.

<Aside type="caution" title="This makes one SVG a reasonable design, not a universal one">

A single correctly-authored SVG does not need a light/dark pair of files.
Document it accurately, though: it follows the _host's_ chosen theme in Chromium and Firefox, and the _viewer's OS_ setting in Safari.
The Safari gap is an engine limitation with no authoring fix, and no `.mmd` directive, render flag, or CSS trick on the embedding page changes it.
It degrades safely.
A Safari reader still sees a light or dark map matching their own system, and the only cost is that it may not match the host page's theme when the two disagree.
Nothing breaks, corrupts, or gets stuck.
One file is a reasonable choice on those terms, because the host controls the result on the two engines that cover most audiences and the third stays adaptive to a different signal.
Claiming the host's toggle drives it everywhere would not be accurate.

</Aside>

<Aside type="note" title="A real example: the nf-core/rnaseq README map">

[nf-core/rnaseq](https://github.com/nf-core/rnaseq) embeds its pipeline map the ordinary way, as `![...](docs/images/..._animated.svg)`, which GitHub renders as a plain `<img>`.
Its map uses the paired `nfcore` theme with a light/dark logo pair, `self_color_scheme` left at its default, and no other flags.
On the rendered page at GitHub that is enough: the whole map, not only the text, follows the GitHub light/dark setting ([source](https://github.com/nf-core/rnaseq/blob/dev/assets/metro_map.mmd)).

</Aside>

For `var()` overrides you have to inline the SVG either way, because nothing in the `<img>` exception carries them.
That is why the nf-metro docs site inlines its maps.

## Reuse the technique outside nf-metro

None of this is specific to nf-metro.
A standalone example:

```html title="index.html"
<!-- [!callout /color-scheme/] Drop this to follow the page's color-scheme instead of the OS. -->
<svg viewBox="0 0 200 100" style="color-scheme: light dark">
  <style>
    rect {
      fill: light-dark(#ffffff, #1a1a1a);
    }
    text {
      fill: light-dark(#111111, #eeeeee);
    }
  </style>
  <rect width="200" height="100" />
  <text x="10" y="50">Adapts to the viewer's theme</text>
</svg>
```

Inline it in an HTML page and it follows the OS preference.
To make it follow a manual toggle on your own site instead, drop the SVG's own `style="color-scheme: light dark"` and drive `color-scheme` from your toggle at the page level, the same way the Starlight `reset.css` does:

```css title="styles.css"
:root {
  color-scheme: dark;
}
:root[data-theme="light"] {
  color-scheme: light;
}
```

```js
// wherever your toggle's click handler lives
document.documentElement.dataset.theme = "light";
```

Any inlined SVG with no `color-scheme` of its own now inherits from `:root` and follows the toggle rather than the OS setting.
