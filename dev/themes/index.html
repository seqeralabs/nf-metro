Themes

A theme decides how a map looks: colors, fonts, station glyphs, section boxes, the legend frame, and optionally layout spacing. It never changes what the map says.

Looking for how one SVG adapts to light and dark viewers? See Light and dark mode.

Concepts

Section titled “Concepts”

Theme. A named set of fields, written as a YAML file. Every built-in theme is such a file in src/nf_metro/themes/, loaded and checked exactly like one you write yourself.

Mode. A theme has a light and a dark palette of colors; sizes and shapes are the same in both. An SVG carries both and follows the viewer’s color-scheme (see Light and dark mode). %%metro mode: or --mode picks the palette baked into a PNG or a single-palette export. A theme whose colors match in both palettes renders the same in either.

Stack. A theme value is a comma-separated list of themes, applied left to right. A later theme wins for every field it sets, and the light and dark palettes merge separately. A single name is a stack of one.

Base. Every stack starts from the default theme, so a theme only needs to set the fields it changes. A map with no %%metro style: renders with default alone.

Layout block. A theme can also set some layout options, such as spacing. The order of precedence is: a command-line flag, then a %%metro directive in the map, then the theme, then the built-in default.

The built-in themes

Section titled “The built-in themes”

Every map below is the same small pipeline, with only its %%metro style: line changed. Each SVG follows this site’s light or dark setting, so switch the site theme to see the other palette. Each theme is a short file in src/nf_metro/themes/, and the files are the best worked examples of the format.

default

Section titled “default”

The base every stack starts from: filled section boxes with number badges, white capsules at stations, bold labels. default.yaml sets every field the schema leaves without a default, so it is the template for a complete theme.

seqera

Section titled “seqera”

Seqera brand colors and Inter type. seqera.yaml replaces the fonts, sizes and both palettes, and leaves the shapes alone.

transparent

Section titled “transparent”

One palette on a transparent canvas, for maps embedded on a page that supplies its own background. transparent.yaml sets every color at the top level, so both palettes match.

london-tube

Section titled “london-tube”

After TfL’s Line Diagram Standard and Colour Standard: tabs in the line’s color at one-line stations, bold capsules at interchanges, a buffer-stop bar at line ends, bundled lines edge to edge, unboxed dashed sections, station names in TfL Corporate Blue, and the TfL line colors.

Rendered map

The standard’s own interchange idiom is rings. Stack a file that sets interchange_glyph: ring on top of london-tube to get them: one ring over two lines, and a bridged chain from three up. Line ends keep the bar, which reads better than a ring there.

nyc-subway

Section titled “nyc-subway”

After Massimo Vignelli’s 1972 diagram and its 2008 revival: every line its own color with only a hairline between them, a small solid black dot wherever a line stops, no separate interchange symbol, tight corners, Helvetica in black, and the legend as round route bullets. The palette is the MTA’s published route colors. In dark mode it takes the white-on-black of the 1970 Graphics Standards Manual’s sign panels.

Rendered map

paris-metro

Section titled “paris-metro”

After the Île-de-France Mobilités metro plan: thin lines nearly touching, a white dot ringed in its line’s color at each stop, black-outlined white capsules at interchanges, wide soft corners, sections on a light grey panel, and a slate legend of numbered line discs. The palette is the IDFM line referential, in line-number order, so the line carrying 1 is line 1’s yellow. In dark mode the six darkest colours lighten to stay readable against the slate background.

Rendered map

tokyo-metro

Section titled “tokyo-metro”

After the Tokyo subway route map and Tokyo Metro’s station numbering mark: every station is its number, a white face ringed in its line’s color around a letter and two digits. A station on several lines is one marker across them, ringed in dark grey. The letter is the station’s section, which the section badge also shows, and the digits count along the section’s flow; a nameless line end has no number and stops at a bar. The palette is Tokyo Metro’s nine line colors, then Toei’s four.

Rendered map

washington-metro

Section titled “washington-metro”

After the Washington Metrorail map: very thick lines a hairline apart, a white dot ringed in black on every line at a stop, broad corners, the Capital Beltway’s pale grey-green band round each section, and legend discs carrying each line’s letter. The palette is WMATA’s six line colors.

Line colors

Section titled “Line colors”

A theme’s line_colors gives the map’s lines their colors, in the order the map declares them. A map with more lines than the list gets a generated color for each extra line: the color farthest, in the perceptual OKLab space, from every color already in use (the palette, earlier extras, the background and the inactive grey), among those readable at 3:1 on the light background. In dark mode each generated color keeps its hue, lightened where it needs to be to reach 3:1 on the dark background, so a line keeps its identity across modes. If the dark palette is shorter than the light one, a dark line past its end takes the light palette’s color at that place, lightened the same way; a light line past the end of a shorter light palette gets a generated color as usual. The palette’s own colors are never changed, and the same map always gets the same extras. Without it, each line keeps the color from its %%metro line: directive.

Set line_colors at the top level for both palettes, or under light: and dark: to give each its own. london-tube does both: the TfL colors in light mode, and in dark mode the same list with the Piccadilly, Metropolitan and Elizabeth colors lightened to stay readable, and the black Northern line turned near-white. A line whose two palette colors differ follows the viewer’s mode in an SVG, as the chrome does.

Station glyphs

Section titled “Station glyphs”

Three fields pick how a station is drawn. The last column names a theme above that draws each one.

FieldValueDrawsSee
station_glyphpilla capsuledefault
(one line)ticka tab in the line’s color, on the label’s sidelondon-tube
dota dot on the line, sized by dot_diameter and outlined by dot_ring_width and dot_ringnyc-subway, paris-metro, washington-metro
numbereda station-number marker ringed in the line’s colortokyo-metro
interchange_glyphpillone capsule across all the linesdefault, london-tube, paris-metro
(several lines)ringa ring centred on the lines, or a bridged chain of themlondon-tube with rings
dotsa dot on each linenyc-subway, washington-metro
numberedone station-number marker across the lines, ringed in station_stroketokyo-metro

(line end)bara buffer-stop bar across the bundlelondon-tube, tokyo-metro

A line end with one line follows station_glyph, and its file icon always sits beyond the glyph.

With ring, ring_max_lines is the most lines on one track that a single ring covers, and ring_overflow decides what a wider bundle gets: chain, the fewest touching rings that cover it, bridged by a strip in the station fill; or grow, one ring whose inside widens to cover it. Lines on separate tracks, as at a cross-track %%metro interchange: or a rail-mode station, get separate rings joined by a dumbbell link.

The legend shows each line as a length of line, or with legend_swatch: bullet as a disc in its color carrying its code (line_codes: letters or numbers), in black or white, whichever reads better.

Corner radius is a layout option, curve_radius_ratio: the radius at the line centre as a multiple of the line width. london-tube sets 3.5, the standard’s three line widths to the inside edge of the line, so its 4 px lines bend at 14 px. Unset, corners bend at 10 px, and stroke_scale scales the radius either way.

Stacking themes

Section titled “Stacking themes”

This map takes the station glyphs, section style, fonts and line colors from london-tube, and every field london-tube leaves unset from seqera. Under both lies default, which supplies anything neither sets. Every stack starts from default; list only the themes you add on top.

A built-in theme sets only the fields its file lists. london-tube, seqera therefore keeps the london-tube station tabs and capsules, because seqera does not set station_glyph or interchange_glyph, but takes the seqera colors and fonts.

Writing your own theme

Section titled “Writing your own theme”
  1. Create a YAML file whose name ends in .yaml or .yml.
  2. Give it a name, then set the fields you want to change. Top-level fields apply to both palettes, and light: and dark: blocks override colors (and line_colors) for one palette. Sizes and shapes are top-level only, because a map is laid out once for both palettes.
  3. Optionally, start from another theme with extends:, and set layout options in a layout: block.
  4. Add the file to a stack. In %%metro style: the path is relative to the .mmd file; on the command line it is relative to the working directory.

extends: is shorthand for listing those themes earlier in the stack, so the line above is the same as %%metro style: london-tube, house_style.yaml. A theme without extends: sits directly on default, like every stack.

A color left empty takes the field its description names: icon and badge colors take the station colors, the marker outline and station-number codes take station_stroke, and knockout_fill (label halos and open markers) takes the background, or white on a transparent canvas.

nf-metro checks the whole file against the theme’s JSON Schema before it renders anything. An unknown field, a value of the wrong type or out of range (including .inf and .nan), a color it cannot read, a size inside light: or dark:, an unknown layout: option, or two files that extend each other stops the render with an error that names the file and the path to the bad value, such as $.light.label_color. Font families, font weights and dash patterns accept only the characters CSS needs for them.

The schema ships with nf-metro as nf_metro/themes/theme.schema.json and is generated from the same definitions as the field reference below. The first line of the example above points editors that use the YAML language server (VS Code’s YAML extension, for one) at it, so they complete field names and flag mistakes as you type. Any other JSON Schema tool can validate a theme file against it too.

Fonts

Section titled “Fonts”

The SVG names the theme’s font and the viewer’s browser draws it, so name a font your readers have, followed by fallbacks. The transit themes ask for the faces their standards use (Gill Sans standing in for Johnston, Helvetica, Parisine, Frutiger) and fall back to common sans faces. PNG output, --embed-font and --text-to-paths draw every theme in the bundled Inter face, so the output is the same on any machine.

Field reference

Section titled “Field reference”

Every field of the Theme schema (src/nf_metro/render/style.py) can be set in a theme file. Default is the schema’s own default, which the default theme overrides for some fields. A colour is a hex value, an rgb()/hsl() function, a CSS color name, transparent or none.

Layout options

Section titled “Layout options”

A layout: block takes these options, with the same values as their %%metro directives: x_spacing, y_spacing, section_x_gap, section_y_gap, section_x_padding, section_y_padding, track_gap, diamond_style, line_order, row_align, center_ports, compact_offsets, label_angle, label_offset, diagonal_run, curve_radius_ratio, font_scale, stroke_scale, logo_scale, legend_min_height, legend_logo_gap, directional. A theme’s value applies only where the map has no directive for that option, and a command-line flag beats both.
